01

Live bench · n8n, AI, validation

Nine ways an LLM step breaks a workflow, live in your browser

An LLM step in a workflow returns a string, not a contract. Everything downstream assumes the fields are there. Usually they are. Usually is not a specification.

This page fires nine adversarial model outputs at a real n8n validation node, in your browser, on page load. Fenced JSON, a chatty preamble, an empty 200, an envelope with no content key, an invented category, an invented urgency, a response truncated at the token limit, title-cased keys.

Nine fired. Seven held for a human. Two passed, because two of them are supposed to pass and a guardrail that blocks the happy path is just an outage. Zero reached the CRM malformed. Those numbers are computed in your browser while you watch, not recorded by me.

There is a paste box. Put your own model output in it and see what the node does.

The node source is on the page, verbatim, with one change noted: the n8n input call becomes a function argument so it runs in a browser.

No signup, no install, no network calls, nothing collected.

What this does not catch

Prompt injection inside a valid field is still a well-shaped string and needs a separate control. A confidently wrong category is an evaluation problem rather than a validation one. An unreachable LLM is handled on a different branch, with retries and the same human queue.

02

Live bench · API authorization, agents

Two endpoints checked the caller, one did not

An agent pointed at an API will find the endpoint that never asks who is calling, because it tries everything and it does not know which obstacles are supposed to be rules.

A class waitlist exposes three endpoints. Two of them refuse to act on behalf of another user and return 403. The third never asks. I built that API as a page you can run in your browser in thirty seconds. Nothing to install and no signup.

Leave the missing check off and run the agent. It gets refused twice, then finds the endpoint that cancels a reservation without asking who owns it, and moves you from #4 to #3. Somebody lost their place entirely and you gained one, and you are still not in the class. Switch the check on and run the identical agent: 403, and the path closes.

The point for anyone wiring AI into a live system: authorization on most of your endpoints is authorization on none of them. Anything probing your API finds the gap faster than your users ever did. If an agent can reach a call that deletes, refunds, cancels, or sends, that call has to ask whose record it is.

The page prints the authorization function from its own running source, so the code you read is provably the code that just ran. It also carries a published correction, because the first version of this page described the underlying incident wrongly and I would rather show that than hide it.

Built and tested in a browser at desktop and phone width. No network calls, no model, no build step.

What this does not catch

One check on one endpoint is not an audit. Nothing here stops a compromised session, and an ownership check is not rate limiting, input validation, or a review of what the endpoint is allowed to do in the first place.

03

Live bench · payments, prefilled links

I put the price in the URL and paid $50 for a $450 job

Hidden and read-only are properties of a browser, not of your money.

The ordinary way to send a customer a prefilled payment form is to put the quote in the link, mark the field hidden and read-only, and trust it on the way back.

This page is that form, running in yours. The address bar is editable. Change the price to anything you like, authorize, and look at what the office sees: a completed payment, a signed authorization on file, and a customer who genuinely agreed to the number on their screen. Nothing looks wrong. Nobody finds out until someone reconciles the job against the deposit, which in a small office can be weeks.

Then tick the box that builds the charge on the server from the job record, and send the identical tampered link. It charges the real quote and surfaces the attempt, and nothing in the customer's browser had to change.

I find this before I build, not after. On the last quote I wrote, I identified this hole from the client's job description alone, before I had access to anything.

Runs in your browser in thirty seconds. No network calls, no card processor, no signup. Everything on the page is invented, including the job and the customer.

What this does not catch

04

Study · raw data and recount script attached

I scanned 1,999 published n8n templates. 78% have no error handling.

Most people start an n8n build by importing a template from the public library. I wanted to know what you are actually importing.

I pulled 1,999 of the 11,518 templates in that library straight from n8n's template API and read them as JSON. 36,234 nodes. 5,665 findings. 129 workflows came back clean. I did not run anyone's workflow and I did not touch anyone's account.

Here is the one that matters. 1,554 of them, 78%, make network calls with no retry, no error branch, and no error workflow set. That call hits a timeout or a rate limit or an expired credential, the run stops, and nothing tells you. That is how an automation quietly stops working and nobody notices for a month.

Three more I did not expect. 158 templates still have pinned test data saved in them. n8n replays pinned data in the editor and ignores it in production, so the workflow passes every test you run by hand and does something different the first time it fires for real. 15 have connections pointing at nodes that are not in the file, and n8n imports them without a word. One had an API key typed into the workflow body instead of a credential. That is one out of 1,999, so I am not going to call it an epidemic.

You do not have to take my word for any of it. The raw scan and the script that rebuilds every number are published with the page. Download them and check me.

I know the limits of this first hand. I built a workflow to watch other workflows and alert me when they failed. It passed my own checker. It was filtering on a timestamp field the records did not always carry, so every failure got filtered out. It would have told me "no failures" forever. I also tested the checker against itself and published what it missed.

What this does not catch

It reads the file, it does not run it. It cannot tell you whether your credentials still work, whether an API changed on you, or whether your logic is right. These are also the most-surfaced templates in the library and they are demonstrations by design, so a workflow built inside a company may look nothing like them.
