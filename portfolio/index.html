Live bench · n8n, AI, validation

Nine ways an LLM step breaks a workflow, live in your browser

An LLM step in a workflow returns a string, not a contract. Everything downstream assumes the fields are there. Usually they are. Usually is not a specification.

This page fires nine adversarial model outputs at a real n8n validation node, in your browser, on page load. Fenced JSON, a chatty preamble, an empty 200, an envelope with no content key, an invented category, an invented urgency, a response truncated at the token limit, title-cased keys.

Nine fired. Seven held for a human. Two passed, because two of them are supposed to pass and a guardrail that blocks the happy path is just an outage. Zero reached the CRM malformed. Those numbers are computed in your browser while you watch, not recorded by me.

There is a paste box. Put your own model output in it and see what the node does.

The node source is on the page, verbatim, with one change noted: the n8n input call becomes a function argument so it runs in a browser.

No signup, no install, no network calls, nothing collected.

What this does not catch

Prompt injection inside a valid field is still a well-shaped string and needs a separate control. A confidently wrong category is an evaluation problem rather than a validation one. An unreachable LLM is handled on a different branch, with retries and the same human queue.

02

Live bench · API authorization, agents

Two endpoints checked the caller, one did not

An agent pointed at an API will find the endpoint that never asks who is calling, because it tries everything and it does not know which obstacles are supposed to be rules.

A class waitlist exposes three endpoints. Two of them refuse to act on behalf of another user and return 403. The third never asks. I built that API as a page you can run in your browser in thirty seconds. Nothing to install and no signup.

Leave the missing check off and run the agent. It gets refused twice, then finds the endpoint that cancels a reservation without asking who owns it, and moves you from #4 to #3. Somebody lost their place entirely and you gained one, and you are still not in the class. Switch the check on and run the identical agent: 403, and the path closes.

The point for anyone wiring AI into a live system: authorization on most of your endpoints is authorization on none of them. Anything probing your API finds the gap faster than your users ever did. If an agent can reach a call that deletes, refunds, cancels, or sends, that call has to ask whose record it is.

The page prints the authorization function from its own running source, so the code you read is provably the code that just ran. It also carries a published correction, because the first version of this page described the underlying incident wrongly and I would rather show that than hide it.

Built and tested in a browser at desktop and phone width. No network calls, no model, no build step.

03

Live bench · payments, prefilled links

I put the price in the URL and paid $50 for a $450 job

Hidden and read-only are properties of a browser, not of your money.

The ordinary way to send a customer a prefilled payment form is to put the quote in the link, mark the field hidden and read-only, and trust it on the way back.

This page is that form, running in yours. The address bar is editable. Change the price to anything you like, authorize, and look at what the office sees: a completed payment, a signed authorization on file, and a customer who genuinely agreed to the number on their screen. Nothing looks wrong. Nobody finds out until someone reconciles the job against the deposit, which in a small office can be weeks.

Then tick the box that builds the charge on the server from the job record, and send the identical tampered link. It charges the real quote and surfaces the attempt, and nothing in the customer's browser had to change.

I find this before I build, not after. On the last quote I wrote, I identified this hole from the client's job description alone, before I had access to anything.

Runs in your browser in thirty seconds. No network calls, no card processor, no signup. Everything on the page is invented, including the job and the customer.

04

Live bench · runs in your browser

The run was green and three orders were gone

Twenty orders, one flaky API, and the only thing that changes between the three runs is the error setting on one node.

The CRM in this bench fails on exactly three of the twenty. ORD-1007 returns a 500 and works on the second attempt. ORD-1013 returns a 429 and works on the third. ORD-1018 returns a 500 every single time, because its payload is genuinely malformed. Two are transient and one is not, which is the whole point: retrying is not the same as handling.

Config B is the dangerous one, and it is the setting most people end up with, because it is what you reach for when you want the red to stop. It does not fail at all as far as anything can tell you. The execution is marked success. The sheet has twenty rows in it. Three of those rows have no order in them. There is no red anywhere on the screen, so nobody looks, and the first time you find out is when a customer asks where their order went.

Config A fails loudly enough to notice. Fourteen orders never get attempted and the execution is flagged as an error, which is bad but visible to anyone who looks. Config C is not perfect either, and the page says so. ORD-1018 is broken and no amount of retrying fixes it. The difference is that C puts it in a named pile and tells a human its name.

The three settings are not invented. n8n's schema defines exactly three node-level error behaviours, and retry is an optional per-node field rather than a default, which is why the study below found 78 percent of templates without it. Both claims are cited on the page against a pinned commit, in a box kept separate from the demo.

It is deterministic. The same three records fail every time you press run, so you can check the arithmetic yourself.

What this does not catch

This is not n8n. It is a model of three documented settings, written in JavaScript, running in your browser. No workflow was executed and no n8n instance was involved. The failure pattern is chosen, not observed: three out of twenty, two transient and one permanent, is a plausible mix that makes the mechanism visible, not a measurement of how often a CRM returns a 500. And it models one node. Real runs also lose data to credential expiry partway through, partial writes, and errors inside sub-workflows.

Live bench · runs in your browser

The account stopped sending and the pipeline kept moving

A GoHighLevel sub-account emails an onboarding sequence to 500 contacts. 40 of the addresses are dead, which happens to every imported list.

Partway through the send, GoHighLevel suspends email for the whole sub-account because the bounce rate crossed its documented threshold. Nothing else stops. Workflows keep running, contacts keep advancing, and the pipeline reports all 500 onboarded. 199 of them were never emailed at all.

The bench runs three configurations of the same send. A is the default path. C is the fix, and it is boring: verify the list first, then send, and nobody is missed.

B is the one to look at, because B is the version a careful person builds. They know bounces matter, so they wire an Email Events trigger filtered on Bounced. It works. They get told about all 25 bounces by name. And it changes nothing about the loss, because the 199 that were never emailed did not bounce, did not trigger anything, and are indistinguishable from the ones that were delivered. GoHighLevel's own FAQ says there is no direct way to find them, and gives a manual export-and-tag workaround instead.

Every claim about GoHighLevel on the page is quoted from its own help articles, one source line each, in a box kept separate from the demo. Twelve quotations, checked against pinned snapshots by a script that exits non-zero if one has drifted by a character. Eight deliberate sabotages of the page, all eight caught, including the one that only moves a full stop to a comma.

The checker has one blind spot and the probe suite keeps it visible: it proves a quotation was said somewhere in the sources, not that the citation beside it names the right article. That blind spot was not theoretical. Checking the citations by hand found one on this page pointing at the wrong article, and it was fixed before publishing rather than after.

What this does not catch

This is not GoHighLevel. It is a model of documented behaviour, written in JavaScript, running in your browser. No account was used and no email was sent. The list of 500 with 40 dead addresses is invented; the thresholds it crosses are documented. The tiered minimum send count introduced on 13 August 2026 is not modelled, because GoHighLevel does not publish the tiers, so on a real account with a lower bounce rate the lock would come later than it does here or not at all. And the claim that the pipeline keeps advancing rests on a quote about workflows in general, not on an observation of this exact sequence.

06

Study · raw data and recount script attached

I scanned 1,999 published n8n templates. 78% have no error handling.

Most people start an n8n build by importing a template from the public library. I wanted to know what you are actually importing.

I pulled 1,999 of the 11,518 templates in that library straight from n8n's template API and read them as JSON. 36,234 nodes. 5,665 findings. 129 workflows came back clean. I did not run anyone's workflow and I did not touch anyone's account.

Here is the one that matters. 1,554 of them, 78%, make network calls with no retry, no error branch, and no error workflow set. That call hits a timeout or a rate limit or an expired credential, the run stops, and nothing tells you. That is how an automation quietly stops working and nobody notices for a month.

Three more I did not expect. 158 templates still have pinned test data saved in them. n8n replays pinned data in the editor and ignores it in production, so the workflow passes every test you run by hand and does something different the first time it fires for real. 15 have connections pointing at nodes that are not in the file, and n8n imports them without a word. One had an API key typed into the workflow body instead of a credential. That is one out of 1,999, so I am not going to call it an epidemic.

You do not have to take my word for any of it. The raw scan and the script that rebuilds every number are published with the page. Download them and check me.

I know the limits of this first hand. I built a workflow to watch other workflows and alert me when they failed. It passed my own checker. It was filtering on a timestamp field the records did not always carry, so every failure got filtered out. It would have told me "no failures" forever. I also tested the checker against itself and published what it missed.

Tool · Python and JavaScript, runs in your browser

n8n Doctor, the scanner behind the 78%

The study published its numbers but not the rules that produced them. So you could check my arithmetic and not read my rules. That is the wrong half to publish.

This is the other half. 16 checks emitting 17 rule ids, in Python and in JavaScript. Paste your own workflow export into the page and it scans in your browser. Nothing is uploaded, and there is no server to upload it to.

Two copies of the same logic is a place for quiet drift, so I did not trust the port. I ran both over a generated corpus and compared every field of every finding: rule, severity, node, detail text, consequence. 91 files, 143 findings, all 17 rules exercised, zero diverging fields.

That test earned its keep on the last file of the run, where the two disagreed. JavaScript always enumerates integer-like object keys first and in numeric order, whatever order they had in the file. So a parameters block written {"2": ..., "1": ...} walked differently in JavaScript than in Python, and any check that stops at the first match named the wrong parameter. Reading the code would not have found that. Diffing the two did. The port now ships its own JSON parser that keeps the source key order.

Then I attacked the test. A script corrupts the JavaScript one mutation at a time and asserts the differential test catches each one. Twelve mutations, and it caught eleven. Broadening a rule from "type ends with .webhook" to "type contains webhook" changed nothing, because no fixture used a lookalike type, so the rule's scope boundary was never tested and a port that quietly widened it would have shipped green. I published that miss rather than quietly fixing it. Two fixtures now pin the boundary and the probe fails without them.

One rule was added after the 1,999 scan finished, so it carries no hit rate anywhere on the page. I am not going to invent one.

What this does not catch

It never runs your workflow. It knows 17 failure shapes, so a clean result means none of those and nothing more. The network-facing node list is a list of name fragments rather than a capability model, which makes the silent-failure count a floor and not a total. Severity is my judgement, not a standard. There is no timeout check, and the page says why I added the webhook auth rule and not that one. It also cannot regenerate the 78% from scratch: the 1,999 workflow bodies were not kept and api.n8n.io disallows re-fetching them.
